Executive readout

下一次可复归的提速，发生在 kernel 之外：冷启动、通信、输入管道和隔离边界必须作为同一个生产面管理。

SGLang v0.5.18 已将 checkpoint staging、TP LMHead 与 allreduce 的重叠做成发布级路径；DeepSeek Harness 则在同一 RC 中处理图像输入复用和 Bubblewrap 逃逸修复；DeepGEMM 的社区 RFC 再把视线推向 MoE 输入生产与 dispatch 的交接。三者不是同一成熟度：一个可评估、一个须按候选版验证、一个只可跟踪。

先迁移缓存，再谈冷启动收益

该版迁至 torch 2.13，缓存统一到 `SGLANG_CACHE_DIR`，首次升级会重新编译；并变更默认 MoE deferred finalize 行为。升级计划需包含旧缓存迁移/预热、关键请求回归和性能基线。

算子库与通信内核

kernel boundary moves upstream
DeepGEMM #410 · 社区 RFC

输入生产的“最后一段等待”可能成为 MoE 重叠的下一处边界

RFC 不改写任何已发布 kernel 性能。它描述的是一个可选的 symmetric-buffer 协议：上游完成一小块 token 的 router、TopK 与 input layout 后，就让下游 dispatch 消费，不再等待整个 mega-batch。讨论本身也指出 progress guarantee 与 buffer 安全复用尚需约定。

证伪条件：必须出现实现，并在固定模型、batch、并行度与输入分布下同时报告端到端 TPOT/吞吐、tail latency、显存与正确性；仅有局部 trace 或单 kernel 时间不能证明整体收益。

深度解读

maturity, cost, falsification
Deep dive 01

重叠正在向上游移动，但“能重叠”不等于“已提速”。

发布级事实 → 冷启动 / TP 通信 → 社区假设 → MoE 输入生产

SGLang 给的是可以复跑的发布级样本：同一 release 中把权重 staging、CUDA graph capture、TP LMHead 与 allreduce 放到明确的模型/硬件/并行配置下，并同时暴露升级代价。它证明这些路径值得 benchmark，不证明每个工作负载都会有相同收益。

DeepGEMM #410 处在更早层级。它要消除的是“等整批输入准备好”的栅栏。若实现后只是让某个局部 kernel 更早开始、却增加同步、buffer 占用或 tail latency，端到端 TPOT 可能不变甚至变差。要把 RFC 升级为结论，至少需要同一输入分布下的前后对照、正确性校验、p50/p99、吞吐和显存峰值。

Deep dive 02

输入面和隔离面不能分开验收。

Harness RC1/RC2 同时处理 Vision-Exp adapter、图像文件复用和 Bubblewrap 逃逸修复。这不是“功能更多”的简单叠加：图像进入系统后的上传、预处理、缓存、会话复用、权限和 sandbox 路径都构成同一个运行契约。

部署动作：先在隔离环境验证 `/proc` 约束与最小权限，再用真实图像工作负载测量 Files API 复用的成功率、延迟和回退；保留可回滚版本。没有这些验证，不能把候选版描述为生产安全或成本更低。

Deep dive 03

升级收益需要包含迁移成本。

冷启动数字很吸引人，但如果升级首次编译、缓存目录迁移或默认 MoE 行为变化造成回归，日常运维收益会被吞掉。把升级拆成预热、功能回归、性能回归、回滚四步，才会得到能长期比较的收益口径。
